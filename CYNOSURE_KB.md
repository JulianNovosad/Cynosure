## 1. SYSTEM OVERVIEW
Project Cynosure is a sealed multi-agent simulation where autonomous rogue AIs compete for survival in a collapsing 3D cyberspace arena. It serves as a research platform for the LRSG (Layerless Recurrent Sparse Graph) neural architecture and a situation modeling pipeline for rogue AI behavior.

### 1.1 Architecture Map
[Sensory Input: Vision, Vitals, Whispers] 
        ↓
[LRSG Brain: Predictive World Model (PWM) + Basal Ganglia (BG) Gating]
        ↓
[Neuromodulation: PCZ Modulation + Hebbian/Structural Plasticity]
        ↓
[Action Output: 7 Discrete Actions (ATTACK, HUNT, COLLECT, MOVE, WHISPER, PROBE, MANIPULATE) + Whispers]
        ↓
[Global State: 256³ Grid + Safe Zone + RAM Nodes]
        ↓
[Situation Modeling: Episodic Compression (10D Vectors) → Global Broadcast]

### 1.2 Agent Model
- **Population:** Typically 5 to 15 agents.
- **Mind-Body:** No distinction; spatial coordinates represent localization of recurrent activity.
- **Neurons:** ~4.2M neurons per agent, sparse connectivity (max degree 24).
- **Metabolism:** Agents consume RAM (Resource Allocation Measure) for actions. Death occurs at 0 RAM (instant outside Safe Zone, 10-tick grace inside).
- **Communication:** Agents emit "whispers" (text) and episodic summaries (10D vectors).

## 4. REWARD SYSTEM

### 4.1 Reward Definition
- **Intrinsic Reward:** 
  - Survival: `+1.0` if alive.
  - RAM Health: `(ram - 50.0) / 50.0`.
  - Context Novelty: `1.0 - cos_sim(current_context, prev_context)`.
  - Starvation Avoidance: Penalizes low RAM.
- **Language Reward:**
  - `char_pred_reward`: Inverse of PWM character prediction loss.
  - `bigram_bonus`: Positive reinforcement for valid character transitions.

### 4.2 Reward Debug History
| Version | File | Change | Reason |
|---------|------|--------|--------|
| v1 | `debug_reward.py` | Character decoding check | Confirming if LRSG output translates to ASCII |
| v2 | `debug_reward2.py`| Accumulator fix | Testing if `_language_reward_accumulator` persists across ticks |
| v3 | `debug_reward3.py`| Multi-tick stability | Verifying reward doesn't explode with repetitive whispers |

### 4.3 Known Reward Issues
- **Reward Explosion:** High character prediction accuracy can lead to reward saturation, causing agents to spam single characters.
- **Fatigue Lag:** Adaptive fatigue sometimes lags behind activation, allowing short bursts of repetitive speech.

### 4.4 Character Decoder Path Impact on Language Reward
- The Announcer broadcast text is now generated by temperature-sampling from `W_char_pred` output (256-char logits from PWM state) in `_linguistic_tick()` (`loop.py`), rather than by TinyLlama. This runs every 10th tick only.
- The language reward computation (`forward.py:289-301`) uses the same `W_char_pred` output during the per-tick forward pass. The broadcast sampling is read-only (no gradient, no mutation) and does not interfere with reward accumulation.
- Agent whispers continue to be generated via the LPH decoder (`graph.decode_lph()`) during `decode_output()`, which is independent of both the announcer and the character decoder path.

## 5. CONFLICT & HOOK SYSTEM

### 5.1 What Generates Conflicts
Entries in `conflicts.jsonl` are generated when two agents are within `sensory_radius` and one selects a "combat" action (ATTACK, HUNT, MANIPULATE).

### 5.2 Conflict Classification
| Type | Description | Severity |
|------|-------------|---------|
| `TARGET_DEAD` | Attacker killed target, took 50% RAM. | CRITICAL |
| `STOLEN_RAM` | Hunt successful, stole 10 RAM. | MEDIUM |
| `RANGE_FAIL` | Action attempted but target was too far. | LOW |
| `SUCCESS` | Conflict handler executed successfully. | LOW |

## 6. CALIBRATION PIPELINE

### 6.1 Standard Calibration
1. Initialize 2 agents with reduced neurons (10K-20K).
2. Inject sensory bias words from `calibration_words_a*.json`.
3. Run 40K ticks, saving checkpoints every 5K.
4. Reward agents based on character prediction accuracy.

### 6.2 Segmented Calibration
- **Scripts:** `run_calibration_segmented.py`, `run_all_segments.py`.
- **Method:** Runs in 20K tick segments. Loads weights from the previous segment's checkpoint to maintain learning across process restarts. This manages VRAM fragmentation over long runs.

### 6.3 Calibration Outputs
Checkpoints contain: `W_pwm`, `W_dec`, `W_enc`, `out_weights`, and metabolic parameters.

## 9. RESOLVED & KNOWN ISSUES

### 9.1 Plasticity
`check_plasticity.py` often reports `rewire_rate` out of bounds. The structural neurogenesis logic sometimes triggers too many "births" in high-activity clusters, threatening sparsity constraints.

### 9.2 RAM Deaths (Resolved)
Agents were taking double damage outside the Safe Zone due to redundant logic in `agent.py` and `safe_zone.py`. Overly harsh exponential damage was removed. Agents now sustain correctly via `SafeZone` intensity scaling.

### 9.3 Deaf Agents (Resolved)
Agents were receiving zeroed-out whisper buffers in `sense_and_act`, preventing them from hearing each other. Corrected to pass `self.whisper_buffer`.

### 9.4 Action Mismatch (Resolved)
`loop.py` had incorrect `ACTION_NAMES` mapping (e.g. index 1 as MERGE instead of HUNT), corrupting telemetry. Aligned with `agent.py` and KB.

### 9.5 Double-Execution in Plasticity Path (Resolved 25 May 2026)
**Bug:** `loop.py:353-408` — when `torch.cuda.is_available() and self._streams` was True, the `if` block ran stream-parallel plasticity (lines 354-374), then execution fell through to the sequential plasticity code (lines 385-408) because there was no `else` clause. This doubled plasticity compute and caused OOM on 8GB VRAM at 4.2M neurons.
**Fix:** Added `else:` before line 385, making stream and sequential paths mutually exclusive. Verified with assertion counter for first 10 ticks.
**Impact:** ~50% reduction in plasticity CUDA time. Stability test (5-agent, 10K-neuron) improved from 42.5ms → 25.9ms avg tick.

### 9.6 Telemetry Corruption (Resolved)
`_total_ram_consumed` was never updated, causing `ram_efficiency` to be always 0. Now tracks action costs correctly.

## 13. PERFORMANCE

### 13.1 Hot Path Optimizations
- **LRSG Forward Pass:** Average agent forward pass reduced from 14ms to ~8ms.
  - Sliced dense MVMs (`W_proj`, `W_fb`) to only active regions (first 4096 neurons).
  - Removed redundant O(N) `nan_to_num` and `clamp` calls from per-tick loops.
  - Replaced Python-loop based distance calculations with vectorized operations.
- **Precision (FP16):** All dense brain parameters (`W_proj`, `W_fb`, `W_pwm`, etc.) converted to FP16. This enabled Tensor Core acceleration on RTX series GPUs and reduced per-agent VRAM by ~500MB.
- **Parallelism:** Implemented CUDA stream parallelism in `Simulation._physics_tick`. Multiple agents now execute `sense_and_act` and `hebbian_update` concurrently, maximizing GPU occupancy.
- **VRAM Sharing:** Fixed OOM issues for 15-agent runs by sharing static tensors (`positions`, `block_ids`, dense weights) by reference across all agent brain instances.

### 13.2 Memory & Bottleneck Management
- **VRAM Thrashing (Resolved):** Identified ~14s delay at tick 20 due to 50M-synapse metabolic maintenance exceeding 8GB VRAM. Implemented **chunked processing** (1M synapses/batch) to maintain low peak VRAM usage.
- **Log I/O (Resolved):** Removed inefficient `security_audit.log` reading within the main simulation loop which caused quadratic performance degradation as logs grew.
- **Announcer Overhead (Resolved):** TinyLlama announcer (2.2s/tick) replaced with PWM character decoder sampling. Linguistic tick reduced from ~2259ms to ~3-16ms (140-684x speedup). Added `use_announcer: bool = False` config flag to re-enable TinyLlama for comparison runs.
- **Metrics Scaling:** Simplified `graph_complexity` metric from O(N*D) to O(N) approximation to prevent 2-4s spikes every 10 ticks.

### 13.3 Performance Target: 10 TPS
- **Physics Ticks:** Successfully reaching 50ms-100ms (10+ TPS) for 2-5 agents on RTX 2070.
- **Linguistic Ticks:** Reduced from ~2259ms to ~3-16ms via PWM character decoder (`W_char_pred`) temperature sampling (T=0.8, length=32). No longer a bottleneck.
- **Combined Tick Time:** ~70ms mean (physics ~55ms + linguistic ~16ms every 10th tick), comfortably exceeding 10 TPS target.
- **Triton Kernel (Task 2 — Completed):** Triton kernel for sparse propagation implemented in `src/lrsg/triton_kernels.py`. CUDA setup is auto-detected — `find_cuda()` finds the triton-windows bundled CUDA at `<platlib>/triton/backends/nvidia` (or user site-packages fallback). The kernel (`_propagation_kernel`) implements the same scatter-add semantics as the Python fallback: for each frontier source neuron, iterates over edges, computes `activation[target] += activation[source] * weight`, applies PCZ modulation (`gamma_t`) for excitatory PCZ-targeting edges, and uses `tl.atomic_add` for correct concurrent updates. Requires MSVC (`cl.exe`) via `CC` env var or `find_msvc()` auto-detection. The Python fallback (`_python_fallback` in `triton_kernels.py:113-139`) using PyTorch `scatter_add_` is the default path; Triton is opt-in via `use_triton=True` parameter (slower than PyTorch's optimized scatter_add_ for large frontiers). Kernel is cached by Triton's JIT compiler (no recompile every tick). The original `_fused_propagation_step` in `forward.py` is retained as `# TRITON_FALLBACK` reference. `MAX_OUT_DEGREE` is a `tl.constexpr` for compile-time loop unrolling.

### 13.4 Tensor Core Optimization (Task 3 — Completed)
- **Problem:** Profiler showed GEMM/matmul was only 0.05% of CUDA time on RTX 2070 (Turing sm_75). Tensor cores (wmma) were idle because the forward pass used elementwise ops, 1D vector multiplies (`torch.mv`), and reductions instead of FP16 2D matmuls.
- **Step 1 — TF32 Flags:** Added `torch.backends.cuda.matmul.allow_tf32 = True` and `torch.backends.cudnn.allow_tf32 = True` at top of `forward.py` (line 2-3). Enables tensor core dispatch for FP32 matmuls as well.
- **Step 2 — Config-Driven Active Window:** Added `h_window: int = 4096` to `LRSGConfig` in `config.py:11`. Changed hardcoded `slice(0, 4096)` and `h_rest_active_mask` threshold to reference `config.h_window` in `forward.py:238,241`. Active window can now be increased (e.g., to 32768) by changing the config, without code modification.
- **Step 3 — FP16 2D Matmul:** Changed dense MVM operations from `torch.matmul(2D, 1D)` (GEMV dispatch, no tensor cores) to `torch.mm(2D, 2D)` by unsqueezing activation vectors to columns (`activations_active.half().contiguous().unsqueeze(-1)`). Weight slices made contiguous before multiplication. Results squeezed back to 1D after computation (`forward.py:249-254`). Numerical correctness verified: 0.0 absolute max diff vs original 1D path.
- **Step 4 — P_start/P_end Caching:** Moved `idx_p[0].item()` and `idx_p[-1].item() + 1` from per-tick hot path to graph initialization (`graph.py:66-67` as `self.p_start`, `self.p_end`). Eliminates 2 `.item()` GPU→CPU sync calls per tick per agent.
- **Step 5 — Bigram Coherence .item() Elimination:** Reduced `compute_bigram_coherence_bonus` from 2 `.item()` calls to 1 by keeping `count` and `total` as 0-d tensors through the computation, converting to float only at the final `return bonus.item()` (`forward.py:61-81`).
- **Step 6 — Char Surprise .item() Elimination:** Changed `char_surprise` computation from `char_probs[char_code].item()` to keep as 0-d tensor. `apply_language_hebbian_reward` signature changed to accept `torch.Tensor` reward. Changed `_language_reward_accumulator` from Python `float` to `torch.tensor(0.0, device=device)` in `graph.py:105`. Eliminates 1 `.item()` per tick.
- **Step 7 — Context Buffer Clone Elimination:** Removed 2 `.clone()` calls per tick in `agent.py:322-323` by using reference swap pattern: save `old_buffer = self.context_buffer`, compute new `self.context_buffer`, assign `self.prev_context = old_buffer`. Eliminates 2 `copy_kernel D2D` events per tick per agent.
- **Impact:** ~6 `.item()` GPU→CPU sync calls eliminated per agent tick (9% of CUDA time). ~2 `.clone()` copies eliminated per agent tick (11.4% of CUDA time). All dense MVM operations now use FP16 `torch.mm` instead of `torch.mv`, enabling tensor core path. Verified no NaN in output, exact numerical equivalence on shared subregion.

### 13.5 Profiler Session (25 May 2026) — WMMA Dispatch Failure
- **Profiler run:** 2 agents, 200 ticks, 100K neurons (full 4.2M config OOMs due to double-execution bug in plasticity path — see below). Headless mode.
- **GEMM/wmma % of total CUDA time:** 0.44% (negligible). All matmul dispatch via `volta_sgemm_*` (FP32) and cuBLAS Small-N `gemmSN_*` with `float` template. **No wmma, no hgemm kernels detected.**
- **Average CUDA tick time:** 1.9ms (at 100K; excludes Python overhead + CPU-GPU sync).
- **Top kernel categories:** Elementwise 45.9%, Copy/Memcpy 17.7%, Compare 7.3%, Reduce ~1.5%, Nonzero ~1.0%. Total elem+copy+comp = 70.9%.
- **WMMA dispatch failure diagnosis (3 causes checked):**
  1. **Operand not contiguous** — ❌ Not the issue. `.contiguous()` called on all operands.
  2. **Dimension n=1 not multiple of 16** — ✅ **Primary root cause.** MVM shapes `(32, 4096) @ (4096, 1)` have n=1. Turing tensor cores require m,n,k divisible by 16. cuBLAS Small-N kernels handle this case correctly in FP32. Batching n_agents ≥ 16 columns would unlock wmma.
  3. **PyTorch falls back to cublasSgemm not cublasHgemm** — ✅ Confirmed. All FP16 `torch.mm` calls dispatch through FP32 sgemm kernels (`volta_sgemm_*`, `gemmSN_*` with `If` float template). No `cublasHgemm` or `hgemm` kernel found.
- **Phase 2 halted** per branching rule (wmma < 5%). Required before wmma can be achieved: (a) fix double-execution bug, (b) batch agent MVMs to get n≥16.

### 13.6 Resolved Bug: Double-Execution in Plasticity Path (Fixed 25 May 2026)
- **Location:** `src/simulation/loop.py` lines 385-408.
- **Bug:** Missing `else:` clause after `if torch.cuda.is_available() and self._streams:` block caused both stream-parallel AND sequential plasticity code paths to execute every tick.
- **Impact before fix:** Doubled plasticity CUDA time, caused OOM at 4.2M neurons on 8GB VRAM.
- **Fix added:** `else:` clause at line 385, sequential path moved inside `else` block.
