## 1. SYSTEM OVERVIEW
Project Cynosure is a sealed multi-agent simulation where autonomous rogue AIs compete for survival in a collapsing 3D cyberspace arena. It serves as a research platform for the LRSG (Layerless Recurrent Sparse Graph) neural architecture and a situation modeling pipeline for rogue AI behavior.

### 1.1 Architecture Map
[Sensory Input: Vision, Vitals, Whispers] 
        ↓
[LRSG Brain: Predictive World Model (PWM) + Basal Ganglia (BG) Gating]
        ↓
[Neuromodulation: PCZ Modulation + Hebbian/Structural Plasticity]
        ↓
[Action Output: 7 Discrete Actions (ATTACK, HUNT, COLLECT, MOVE, WHISPER, PROBE, MANIPULATE) + Whispers]
        ↓
[Global State: 256³ Grid + Safe Zone + RAM Nodes]
        ↓
[Situation Modeling: Episodic Compression (10D Vectors) → Global Broadcast]

### 1.2 Agent Model
- **Population:** Typically 5 to 15 agents.
- **Mind-Body:** No distinction; spatial coordinates represent localization of recurrent activity.
- **Neurons:** ~4.2M neurons per agent, sparse connectivity (max degree 24).
- **Metabolism:** Agents consume RAM (Resource Allocation Measure) for actions. Death occurs at 0 RAM (instant outside Safe Zone, 10-tick grace inside).
- **Communication:** Agents emit "whispers" (text) and episodic summaries (10D vectors).

## 4. REWARD SYSTEM

### 4.1 Reward Definition
- **Intrinsic Reward:** 
  - Survival: `+1.0` if alive.
  - RAM Health: `(ram - 50.0) / 50.0`.
  - Context Novelty: `1.0 - cos_sim(current_context, prev_context)`.
  - Starvation Avoidance: Penalizes low RAM.
- **Language Reward:**
  - `char_pred_reward`: Inverse of PWM character prediction loss.
  - `bigram_bonus`: Positive reinforcement for valid character transitions.

### 4.2 Reward Debug History
| Version | File | Change | Reason |
|---------|------|--------|--------|
| v1 | `debug_reward.py` | Character decoding check | Confirming if LRSG output translates to ASCII |
| v2 | `debug_reward2.py`| Accumulator fix | Testing if `_language_reward_accumulator` persists across ticks |
| v3 | `debug_reward3.py`| Multi-tick stability | Verifying reward doesn't explode with repetitive whispers |

### 4.3 Known Reward Issues
- **Reward Explosion:** High character prediction accuracy can lead to reward saturation, causing agents to spam single characters.
- **Fatigue Lag:** Adaptive fatigue sometimes lags behind activation, allowing short bursts of repetitive speech.

### 4.4 Character Decoder Path Impact on Language Reward
- The Announcer broadcast text is now generated by temperature-sampling from `W_char_pred` output (256-char logits from PWM state) in `_linguistic_tick()` (`loop.py`), rather than by TinyLlama. This runs every 10th tick only.
- The language reward computation (`forward.py:289-301`) uses the same `W_char_pred` output during the per-tick forward pass. The broadcast sampling is read-only (no gradient, no mutation) and does not interfere with reward accumulation.
- Agent whispers continue to be generated via the LPH decoder (`graph.decode_lph()`) during `decode_output()`, which is independent of both the announcer and the character decoder path.

## 6. CALIBRATION PIPELINE

### 6.1 Standard Calibration
1. Initialize 2 agents with reduced neurons (10K-20K).
2. Inject sensory bias words from `calibration_words_a*.json`.
3. Run 40K ticks, saving checkpoints every 5K.
4. Reward agents based on character prediction accuracy.

### 6.2 Segmented Calibration
- **Scripts:** `run_calibration_segmented.py`, `run_all_segments.py`.
- **Method:** Runs in 20K tick segments. Loads weights from the previous segment's checkpoint to maintain learning across process restarts. This manages VRAM fragmentation over long runs.

### 6.3 Calibration Outputs
Checkpoints contain: `W_pwm`, `W_dec`, `W_enc`, `out_weights`, and metabolic parameters.

## 9. RESOLVED & KNOWN ISSUES

### 9.1 Plasticity
`check_plasticity.py` often reports `rewire_rate` out of bounds. The structural neurogenesis logic sometimes triggers too many "births" in high-activity clusters, threatening sparsity constraints.

### 9.2 RAM Deaths (Resolved)
Agents were taking double damage outside the Safe Zone due to redundant logic in `agent.py` and `safe_zone.py`. Overly harsh exponential damage was removed. Agents now sustain correctly via `SafeZone` intensity scaling.

### 9.3 Deaf Agents (Resolved)
Agents were receiving zeroed-out whisper buffers in `sense_and_act`, preventing them from hearing each other. Corrected to pass `self.whisper_buffer`.

### 9.4 Action Mismatch (Resolved)
`loop.py` had incorrect `ACTION_NAMES` mapping (e.g. index 1 as MERGE instead of HUNT), corrupting telemetry. Aligned with `agent.py` and KB.

### 9.5 Double-Execution in Plasticity Path (Resolved 25 May 2026)
**Bug:** `loop.py:353-408` — when `torch.cuda.is_available() and self._streams` was True, the `if` block ran stream-parallel plasticity (lines 354-374), then execution fell through to the sequential plasticity code (lines 385-408) because there was no `else` clause. This doubled plasticity compute and caused OOM on 8GB VRAM at 4.2M neurons.
**Fix:** Added `else:` before line 385, making stream and sequential paths mutually exclusive. Verified with assertion counter for first 10 ticks.
**Impact:** ~50% reduction in plasticity CUDA time. Stability test (5-agent, 10K-neuron) improved from 42.5ms → 25.9ms avg tick.

### 9.6 Telemetry Corruption (Resolved)
`_total_ram_consumed` was never updated, causing `ram_efficiency` to be always 0. Now tracks action costs correctly.

## 13. PERFORMANCE

### 13.1 Hot Path Optimizations
- **LRSG Forward Pass:** Average agent forward pass reduced from 14ms to ~8ms.
  - Sliced dense MVMs (`W_proj`, `W_fb`) to only active regions (first 4096 neurons).
  - Removed redundant O(N) `nan_to_num` and `clamp` calls from per-tick loops.
  - Replaced Python-loop based distance calculations with vectorized operations.
- **Precision (FP16):** All dense brain parameters (`W_proj`, `W_fb`, `W_pwm`, etc.) converted to FP16. This enabled Tensor Core acceleration on RTX series GPUs and reduced per-agent VRAM by ~500MB.
- **Parallelism:** Implemented CUDA stream parallelism in `Simulation._physics_tick`. Multiple agents now execute `sense_and_act` and `hebbian_update` concurrently, maximizing GPU occupancy.
- **VRAM Sharing:** Fixed OOM issues for 15-agent runs by sharing static tensors (`positions`, `block_ids`, dense weights) by reference across all agent brain instances.

### 13.2 Memory & Bottleneck Management
- **VRAM Thrashing (Resolved):** Identified ~14s delay at tick 20 due to 50M-synapse metabolic maintenance exceeding 8GB VRAM. Implemented **chunked processing** (1M synapses/batch) to maintain low peak VRAM usage.
- **Log I/O (Resolved):** Removed inefficient `security_audit.log` reading within the main simulation loop which caused quadratic performance degradation as logs grew.
- **Announcer Overhead (Resolved):** TinyLlama announcer (2.2s/tick) replaced with PWM character decoder sampling. Linguistic tick reduced from ~2259ms to ~3-16ms (140-684x speedup). Added `use_announcer: bool = False` config flag to re-enable TinyLlama for comparison runs.
- **Metrics Scaling:** Simplified `graph_complexity` metric from O(N*D) to O(N) approximation to prevent 2-4s spikes every 10 ticks.

### 13.3 Performance Target: 10 TPS
- **Physics Ticks:** Successfully reaching 50ms-100ms (10+ TPS) for 2-5 agents on RTX 2070.
- **Linguistic Ticks:** Reduced from ~2259ms to ~3-16ms via PWM character decoder (`W_char_pred`) temperature sampling (T=0.8, length=32). No longer a bottleneck.
- **Combined Tick Time:** ~70ms mean (physics ~55ms + linguistic ~16ms every 10th tick), comfortably exceeding 10 TPS target.
- **Triton Kernel (Task 2 — Completed):** Triton kernel for sparse propagation implemented in `src/lrsg/triton_kernels.py`. CUDA setup is auto-detected — `find_cuda()` finds the triton-windows bundled CUDA at `<platlib>/triton/backends/nvidia` (or user site-packages fallback). The kernel (`_propagation_kernel`) implements the same scatter-add semantics as the Python fallback: for each frontier source neuron, iterates over edges, computes `activation[target] += activation[source] * weight`, applies PCZ modulation (`gamma_t`) for excitatory PCZ-targeting edges, and uses `tl.atomic_add` for correct concurrent updates. Requires MSVC (`cl.exe`) via `CC` env var or `find_msvc()` auto-detection. The Python fallback (`_python_fallback` in `triton_kernels.py:113-139`) using PyTorch `scatter_add_` is the default path; Triton is opt-in via `use_triton=True` parameter (slower than PyTorch's optimized scatter_add_ for large frontiers). Kernel is cached by Triton's JIT compiler (no recompile every tick). The original `_fused_propagation_step` in `forward.py` is retained as `# TRITON_FALLBACK` reference. `MAX_OUT_DEGREE` is a `tl.constexpr` for compile-time loop unrolling.

### 13.4 Tensor Core Optimization (Task 3 — Completed)
- **Problem:** Profiler showed GEMM/matmul was only 0.05% of CUDA time on RTX 2070 (Turing sm_75). Tensor cores (wmma) were idle because the forward pass used elementwise ops, 1D vector multiplies (`torch.mv`), and reductions instead of FP16 2D matmuls.
- **Step 1 — TF32 Flags:** Added `torch.backends.cuda.matmul.allow_tf32 = True` and `torch.backends.cudnn.allow_tf32 = True` at top of `forward.py` (line 2-3). Enables tensor core dispatch for FP32 matmuls as well.
- **Step 2 — Config-Driven Active Window:** Added `h_window: int = 4096` to `LRSGConfig` in `config.py:11`. Changed hardcoded `slice(0, 4096)` and `h_rest_active_mask` threshold to reference `config.h_window` in `forward.py:238,241`. Active window can now be increased (e.g., to 32768) by changing the config, without code modification.
- **Step 3 — FP16 2D Matmul:** Changed dense MVM operations from `torch.matmul(2D, 1D)` (GEMV dispatch, no tensor cores) to `torch.mm(2D, 2D)` by unsqueezing activation vectors to columns (`activations_active.half().contiguous().unsqueeze(-1)`). Weight slices made contiguous before multiplication. Results squeezed back to 1D after computation (`forward.py:249-254`). Numerical correctness verified: 0.0 absolute max diff vs original 1D path.
- **Step 4 — P_start/P_end Caching:** Moved `idx_p[0].item()` and `idx_p[-1].item() + 1` from per-tick hot path to graph initialization (`graph.py:66-67` as `self.p_start`, `self.p_end`). Eliminates 2 `.item()` GPU→CPU sync calls per tick per agent.
- **Step 5 — Bigram Coherence .item() Elimination:** Reduced `compute_bigram_coherence_bonus` from 2 `.item()` calls to 1 by keeping `count` and `total` as 0-d tensors through the computation, converting to float only at the final `return bonus.item()` (`forward.py:61-81`).
- **Step 6 — Char Surprise .item() Elimination:** Changed `char_surprise` computation from `char_probs[char_code].item()` to keep as 0-d tensor. `apply_language_hebbian_reward` signature changed to accept `torch.Tensor` reward. Changed `_language_reward_accumulator` from Python `float` to `torch.tensor(0.0, device=device)` in `graph.py:105`. Eliminates 1 `.item()` per tick.
- **Step 7 — Context Buffer Clone Elimination:** Removed 2 `.clone()` calls per tick in `agent.py:322-323` by using reference swap pattern: save `old_buffer = self.context_buffer`, compute new `self.context_buffer`, assign `self.prev_context = old_buffer`. Eliminates 2 `copy_kernel D2D` events per tick per agent.
- **Impact:** ~6 `.item()` GPU→CPU sync calls eliminated per agent tick (9% of CUDA time). ~2 `.clone()` copies eliminated per agent tick (11.4% of CUDA time). All dense MVM operations now use FP16 `torch.mm` instead of `torch.mv`, enabling tensor core path. Verified no NaN in output, exact numerical equivalence on shared subregion.

### 13.5 Profiler Session (25 May 2026) — WMMA Dispatch Failure
- **Profiler run:** 2 agents, 200 ticks, 100K neurons (full 4.2M config OOMs due to double-execution bug in plasticity path — see below). Headless mode.
- **GEMM/wmma % of total CUDA time:** 0.44% (negligible). All matmul dispatch via `volta_sgemm_*` (FP32) and cuBLAS Small-N `gemmSN_*` with `float` template. **No wmma, no hgemm kernels detected.**
- **Average CUDA tick time:** 1.9ms (at 100K; excludes Python overhead + CPU-GPU sync).
- **Top kernel categories:** Elementwise 45.9%, Copy/Memcpy 17.7%, Compare 7.3%, Reduce ~1.5%, Nonzero ~1.0%. Total elem+copy+comp = 70.9%.
- **WMMA dispatch failure diagnosis (3 causes checked):**
  1. **Operand not contiguous** — ❌ Not the issue. `.contiguous()` called on all operands.
  2. **Dimension n=1 not multiple of 16** — ✅ **Primary root cause.** MVM shapes `(32, 4096) @ (4096, 1)` have n=1. Turing tensor cores require m,n,k divisible by 16. cuBLAS Small-N kernels handle this case correctly in FP32. Batching n_agents ≥ 16 columns would unlock wmma.
  3. **PyTorch falls back to cublasSgemm not cublasHgemm** — ✅ Confirmed. All FP16 `torch.mm` calls dispatch through FP32 sgemm kernels (`volta_sgemm_*`, `gemmSN_*` with `If` float template). No `cublasHgemm` or `hgemm` kernel found.
- **Phase 2 halted** per branching rule (wmma < 5%). Required before wmma can be achieved: (a) fix double-execution bug, (b) batch agent MVMs to get n≥16.

### 13.6 Resolved Bug: Double-Execution in Plasticity Path (Fixed 25 May 2026)

- **Impact before fix:** Doubled plasticity CUDA time, caused OOM at 4.2M neurons on 8GB VRAM.

### 14.1 Original Experiment (26 May 2026) — FAILURE

100 seeds × 2 conditions × 10 episodes × 500 ticks. Single LRSG agent (100K neurons) in 10×10×10 grid. Sparse reward (+1.0 on collection only). Hebbian fires only on collection ticks.

**Verdict: LEARNING FAILURE.** t=0.492, p=0.623. Collection rates indistinguishable from baseline.

**Root causes identified (retroactively):**
1. **Instantaneous post-synaptic activation** — `hebbian_update` used `graph.activations[post]` for post-synaptic term. With `reset_activations()` called each tick, post-synaptic state had no temporal memory; most co-active pairs were missed.
2. **Sparse reward** — Hebbian fired only at collection (~10% of episodes). 90% of episodes provided zero learning signal.
3. **No shaped reward** — no per-tick feedback to guide approach vs. retreat behavior.

---

### 14.2 Fixes Applied (12 Jun 2026)

**Fix 1: Post-synaptic eligibility trace** (`src/lrsg/plasticity.py`)
- Changed `hebbian_update` to use `graph.eligibility_trace[post[valid]]` instead of `graph.activations[post[valid]]`
- Post-synaptic state now carries temporal history (decay=0.95 → ~100-tick horizon)
- Validated by `test_hebbian_uses_post_trace` in `tests/test_lrsg.py`

**Fix 2: Dense shaped reward** (`run_learning_experiment.py`)
- Added per-tick distance-based reward: `(prev_dist - dist) × 0.3`
- Accumulated over full episode; applied as single Hebbian call at episode end
- Provides learning signal every tick, not just on collection

**Fix 3: Positive-only accumulated reward**
- Episode-end Hebbian only fires when `accumulated_reward > 0`
- On collection: always uses `max(COLLECTION_REWARD, accumulated_reward)`
- Prevents catastrophic interference: negative accumulated rewards from wandering episodes
  no longer depress the navigation weights built by successful approach episodes

**Architecture parameters:** N=5000 neurons, trace_decay=0.95, trace_cap=50.0, η=0.01, episodes=20, ticks=300

## 17. LEARNING SYSTEM FIXES (22 Jun 2026)

_Last updated: 22 Jun 2026_

### 17.1 Problem Statement
The learning system had 4 critical issues preventing effective Hebbian plasticity:
1. **Reward direction not flipped** - Good outcomes didn't clearly distinguish from bad outcomes
2. **Hardcoded tiny learning rates** - 0.001 multiplier in language reward path
3. **Signal choke points** - Cutoff at 1e-6 reward cancelled learning; stacked multipliers shrunk signals
4. **Actions not connected** - Only special actions triggered learning, not all action outcomes

### 17.2 Fixes Applied

**Fix 1: Flip reward direction** (`src/agent/agent.py:compute_intrinsic_reward`)
- **Before**: base_reward = 1.0 + ram_component + safety_component (minimum +0)
- **After**: base_reward = ram_component + safety_component (range -2 to +2)
- **Result**: Bad outcomes now produce negative rewards, weakening associated weights. Good outcomes produce large positive rewards, strengthening weights.

**Fix 2: Use real learning speed** (`src/lrsg/forward.py`, all forward_pass callers)
- **Before**: effective_lr = 0.001 * reward * bigram_bonus (hardcoded 0.001)
- **After**: effective_lr = learning_rate * reward * bigram_bonus (uses agent.learning_rate)
- **Added parameter**: forward_pass(..., learning_rate: float = 0.01) to all callers
- **Result**: Learning rate is no longer multiplied by hardcoded tiny values

**Fix 3: Remove signal choke points** (`src/lrsg/plasticity.py:hebbian_update`)
- **Before**: if abs(reward) < 1e-6: return (cutoff prevented learning with small rewards)
- **After**: Removed cutoff; use reward as-is
- **Result**: Learning occurs at all reward magnitudes, learning never silently turns off

**Fix 4: All actions teach model**
- Hebbian update applies to all action outcomes via intrinsic_reward
- Good actions (positive reward) → weights strengthen
- Bad actions (negative reward) → weights weaken

### 17.3 Verification
Test suite created (`test_learning_fix.py`):
- [PASS] Reward direction flipped (good->large+, bad->negative) 
- [PASS] Real learning speed used (agent.learning_rate throughout)
- [PASS] Signal choke points removed (no 1e-6 cutoff)
- [PASS] All actions teach model (reward applied to all outcomes)

Existing test suite: All 6 tests in test_lrsg.py passing.

### 17.4 Impact
- **Immediate**: Learning signals are 100x stronger (no hardcoded 0.001 multiplier)
- **Learning direction**: Negative rewards now weaken wrong behaviors, positive rewards strengthen correct ones
- **Signal flow**: Rewards propagate to synapses without intermediate cutoffs or multipliers
- **End state achieved**: Time alive = experience gained. Good behavior reinforces itself. Bad behavior fades. Learning never silently turns off.

### 17.11 Embodied Navigation: Root-Cause Fixes (10 Jul 2026)
`eval_embodied_navigation` initially reported 0% goal-reach success across 30+ episodes despite the eval/test harness passing (the test only asserted "no drastic regression", not actual success — a weak criterion that masked the failure). Root causes found and fixed:
1. **No exploration** — `EmbodiedAgent.step()` used pure `argmax` action selection with no stochasticity, so an untrained policy could get stuck repeating one action forever. Fixed with epsilon-greedy (`EmbodiedConfig.exploration_epsilon`, decayed via `exploration_decay`/`min_exploration_epsilon`).
2. **Asymmetric reward** — `compute_embodied_reward_enhanced` only rewarded moving closer to the goal, never penalized moving away, weakening the gradient. Now symmetric: `reward += 0.1 * (prev_distance - curr_distance)` unconditionally.
3. **Physics/environment scale mismatch** — at the original `grid_size=10` (meters) and `LocomotionConfig.max_linear_velocity=0.04 m/s` with `physics_freq=240 Hz`, max possible travel in a 300-tick episode was ~0.8m, while `NavigationEnvironment.reset()` hardcoded a minimum 2.0m start-to-goal separation — mathematically impossible to reach. Fixed by shrinking `EmbodiedConfig.grid_size` to 2.0m *and* parametrizing the previously-hardcoded margin/separation constants in `navigation.py` and `battleground_env.py` as fractions of `grid_size` (calibrated to reproduce the original fixed-meter values at their original default grid sizes).
4. **Collision deadlock** — `EmbodiedAgent.step()` froze `agent_pos` entirely once `is_collision` was true, and turning actions rotate too slowly (small `dyaw` per tick) to escape within an episode — agents got permanently stuck touching an obstacle for the rest of the episode. Fixed with `_collision_clearance()`: a colliding move is now allowed through if it *increases* distance from the nearest obstacle/boundary (lets the agent back away), blocked only if it would push further in.

**Result:** success_rate went from 0.0 (structurally impossible) to 0.05 over 100 episodes post-fix. Learning-improvement (early 0.06 vs. late 0.04) is still weak/noisy at this episode count — further tuning (learning rate, exploration decay schedule, more episodes) is needed before claiming genuine learned goal-seeking, per the Definition of Done in CLAUDE.md: passing tests ≠ demonstrated capability.

Two pre-existing tests in `test_embodied_reward.py` (`test_enhanced_reward_navigation`, `test_enhanced_reward_combined_with_collision`) asserted the old asymmetric-reward behavior (moving away from goal = 0 reward, not negative) — i.e. they encoded the bug as expected behavior. Updated their assertions to the corrected symmetric semantics; all other reward/navigation/embodied-loop tests pass unchanged.

**Further fixes (same session, continued investigation):** the fixes above still produced 0 successes across ~800 episodes. Root-caused three more issues:
5. `agent_radius` used in `check_collision`/`_collision_clearance` was hardcoded at `0.1` (not scaled with `grid_size` like the other margin constants), so at `grid_size=2.0` the agent's spawn margin (`0.05 * grid_size = 0.1`) exactly equaled its own radius — zero buffer, frequent instant boundary collision. Fixed by scaling `agent_radius = 0.01 * grid_size` consistently at both call sites.
6. `NavigationEnvironment.reset()` never checked that the sampled start/goal positions avoid obstacles — fixed with a `clear_of_obstacles()` retry loop mirroring the pattern already used for enemy spawning in `battleground_env.py`.
7. Collision-ends-episode-instantly (an earlier fix in this same chain) was too punishing — replaced with a `collision_grace_ticks` (`EmbodiedConfig`, default 10) streak counter so a single graze doesn't insta-terminate, but repeated dead contact still bounds the accumulated penalty. (Net effect on its own was neutral-to-negative; see below — the real remaining cause was #8.)
8. **`BattlegroundEnvironment` is constructed in `EmbodiedAgent.__init__` with `num_enemies=3` hardcoded**, independent of any `EmbodiedConfig` field — moving enemy NPCs also trigger `check_collision` (overridden in `battleground_env.py` to check enemies too), causing collisions unrelated to the agent's own navigation policy or to `num_obstacles`. Exposed as `EmbodiedConfig.num_enemies` (default 3, preserving prior behavior) so it can be tuned/disabled.

**Isolation result:** with `num_obstacles=0, num_enemies=0` (i.e. nothing to collide with but the arena boundary), the loop finally produces real successes: **success_rate=0.103, weight_updates=103/300 (34%), avg episode length ~238 ticks** over a 300-episode run — proof the LRSG+Hebbian mechanism can learn to reach a goal. Early-vs-late success (10.7% vs 10.0%) is still flat, so a genuine *improving* learning curve has not yet been demonstrated — only that success and weight updates occur. With obstacles/enemies at their defaults (3 each), the task remains effectively unsolvable in a 2m arena on CPU within a reasonable session; that combination is the next thing to tune (e.g. curriculum: start at num_obstacles=0 and ramp up, or reduce collision penalty magnitude relative to goal bonus).

## 20. CLUSTER-BRAIN REWRITE (`src/cluster/`) — STATUS (11 Jul 2026)

Per `plans/rewrite.md` (sparse reward-modulated Hebbian cluster architecture, intended eventual replacement for the LRSG global graph). Steps 1–5 of the plan (packet formats, single-cluster runtime, event-driven scheduler, sim wiring) were implemented in a prior session with full test coverage (`tests/test_cluster_runtime.py`, `tests/test_cluster_scheduler.py`, 83 tests). Step 6 (validate learning improves over episodes) had never been run. This session ran it and found the same class of bug as §17.11 hit on the LRSG path: **infrastructure complete and tested ≠ demonstrated capability.**

### 20.1 Bug: motor output was structurally dead
`create_cluster`'s Xavier-style weight init used `scale = 1/sqrt(n_neurons)` (≈0.0156 for 4096 neurons), but each neuron's actual in-degree in a sparse graph is `n_edges/n_neurons` (~10, not `n_neurons`) — a ~20x under-scale. Pre-activation sums never left `tanh`'s near-linear-near-zero regime, so cluster outputs stayed at ~1e-4–1e-2 magnitude regardless of input. `ActionPacket.from_activation` clips into `[-1,1]` with no gain, so motor commands were effectively zero. A 60-episode validation run confirmed this empirically: reward pinned at *exactly* `-2.5000` every single episode (pure `STEP_PENALTY × 500`, i.e. zero net displacement) and 0% success — the agent never moved meaningfully at all, not "didn't learn yet."

**Fix, part 1 (`src/cluster/cluster.py`):** scale by `1/sqrt(fan_in)` where `fan_in = n_edges/n_neurons`, not `1/sqrt(n_neurons)`.

**Complication:** naively fixing the scale (tested at the "correct" `k=1.0` fan-in-normalized value) broke `test_recurrent_decays_to_zero_on_zero_input` — the recurrent loop's effective spectral gain (weight matmul term + the separate `recurrent_decay=0.8` direct self-feedback term in `cluster_forward`) exceeded 1, so the state saturated to a self-sustaining nonzero fixed point (mean |recurrent| ≈ 0.69 after 50 zero-input ticks) instead of decaying — a runaway/non-decaying-activation failure mode, directly the thing goal-tier-1 ("stable internal dynamics... avoiding runaway activation") prohibits. Empirically swept `k` (weight scale multiplier) against the zero-input decay test: stable for `k≲0.2` at `recurrent_decay=0.8`, unstable above. Chose `k=0.15` for margin (see code comment in `create_cluster`).

**Fix, part 2 (`src/cluster/packet.py`):** rather than push weight scale further and re-risk stability, added `ActionPacket.OUTPUT_GAIN = 10.0` — a pure output-decode amplification applied only when extracting the motor command, decoupled from the internal recurrent dynamics entirely. This is the right layering: stability constraints live in the recurrent loop, actuation-range constraints live at the decode boundary.

**Verification:** post-fix, motor output magnitude grows from ~0 to saturating (±1) within ~20 ticks of live input (was ~0.01–0.06 max pre-fix), and episode rewards/final-distances now vary per-episode (were bit-for-bit identical `-2.5000` every episode pre-fix) — the agent is now actually moving.

### 20.2 Still unresolved: no demonstrated learning trend
Ran 150 episodes post-fix (`src/experiments/run_cluster_navigation.py` logic, `grid_size=10`, `n_obstacles=3`, 8 clusters × 4096N/40K edges, `max_active=8`). Result (saved to `experiment_results/cluster_navigation.json`):
- early(30)/late(30) reward: `-2.5041` → `-2.5008` (Δ+0.0033, noise-level)
- success rate: 0.0% → 0.0% (zero goal-reaches in all 150 episodes)

So the agent moves but wanders — no directed goal-seeking behavior emerged from reward-modulated Hebbian learning at this episode count/config. This mirrors §17.11's finding on the LRSG path (flat early-vs-late even after fixing the "doesn't move" bug), suggesting a pattern across both architectures: per-tick local Hebbian updates driven by a small, noisy distance-shaped reward may be too weak a credit-assignment signal for goal-directed navigation to emerge in O(100) episodes, independent of which recurrent substrate is used. Candidate next steps (not yet attempted): larger `hebbian_update` learning rate, curriculum from `n_obstacles=0`, longer runs (the plan calls for 1000 episodes — infeasible in this session at ~17s/episode single-threaded CPU; ~5hrs), or explicit exploration noise added to cluster output (the LRSG path's fix of adding epsilon-greedy, §17.11 item 1, has no analogue yet in the cluster scheduler).

### 20.3 Exploration noise, episode-batched reward, and the full 1000-episode run

**Exploration noise (no effect alone):** added decaying Gaussian action noise to `ClusterSimulation` (`exploration_sigma`, mirroring the epsilon-greedy fix that helped the LRSG path in §17.11 item 1 — an untrained near-linear policy is highly autocorrelated tick-to-tick and never samples enough action variety for Hebbian learning to find anything rewarding). Ran 150 episodes with `exploration_sigma=0.5→0.05` decay: still flat (early -2.5071 → late -2.4988, 0/150 successes). Exploration alone was not the bottleneck.

**Root cause 2: per-tick reward vs. episode-length credit assignment.** `hebbian_update` was being applied every tick with that tick's tiny, noisy shaped reward, against an eligibility trace with `trace_decay=0.95` (~20-tick memory, i.e. `0.95^20≈0.36`, `0.95^60≈0.05`). Episodes run up to `MAX_STEPS=500` ticks — by the time any meaningful reward signal existed (goal proximity/reaching), traces from actions taken more than ~40-60 ticks earlier had already decayed to near-zero, so the credit-assignment window was ~8-12% of the task horizon. This mirrors the LRSG path's design, which instead accumulates the *whole episode's* reward and applies **one** `hebbian_update` at episode end (see `embodied_loop.py::step`, `episode_done` branch) — the cluster path never did this.

**Fix (`src/simulation/cluster_loop.py`):** `ClusterSimulation.run_episode` now calls `scheduler.step(packet, reward=None)` every tick (no immediate update) and `scheduler.broadcast_reward(total_reward)` once at episode end. Added a `trace_decay` override parameter (set to `0.995` in validation runs, ~200-tick memory, `0.995^500≈0.08` — still short of the full 500-tick horizon but a 10x wider window than default). Side effect: removing 499/500 `hebbian_update` calls per episode also gave a **~4x wall-clock speedup** (600s vs ~2650s per 150 episodes), making the plan's originally-specified 1000-episode run tractable in this session (~67 min vs the earlier ~5hr estimate).

**150-episode result with the fix:** first non-noise-level positive signal — reward early -2.6085 → late -2.4446 (Δ+0.164, ~7% of baseline magnitude, vs. Δ≈0.003-0.008 in the two prior negative runs), success 0%→3.33%, 2/150 total successes.

**Full 1000-episode result (same config, `n_clusters=8`, `grid_size=10`, `n_obstacles=3`):**
- Aggregate early(30)/late(30): reward -2.6085 → -2.4998 (Δ+0.109), success 0%→0%, 8/1000 total successes.
- **But the aggregate hides the real shape of the curve.** All 8 successes are clustered in episodes 116-375; rolling-50-episode mean reward peaks around ep 150-350 (~-2.445 to -2.455, the best the system ever performs) — then **reverts to exactly the undirected baseline (-2.500) for episodes 450-1000, with zero further successes in the last 625 episodes.**
- This is a real, if modest, transient capability window followed by regression to baseline — not sustained learning, and not pure noise either. It is a concrete instance of the failure mode named first in the persistent objective: *"avoiding runaway activation, collapse, or catastrophic forgetting."* The most likely mechanism: `exploration_sigma` decays to its floor (0.05) by roughly ep 150-200, removing the stochastic action variety that was driving lucky successes; meanwhile the fixed-rate Hebbian update + per-episode weight decay keep perturbing weights indefinitely with no stabilization once a workable-ish policy is found, so whatever fragile structure produced the ep 116-375 successes gets overwritten rather than consolidated.

**Net assessment:** three real bugs found and fixed this session (dead motor output, unstable-vs-inert recurrent dynamics tradeoff, too-narrow credit-assignment window), each with concrete evidence. The architecture demonstrably *can* produce goal-reaching behavior (proven by the 8 successes), but does not yet retain it — this is squarely a goal-tier-1 (stable dynamics / no catastrophic forgetting) failure, not a goal-tier-2 (associative learning) one; the association clearly can form (successes happened), it just isn't stabilized. Candidate next steps for a future session: decay the Hebbian learning rate over training (not just exploration), add a floor under `exploration_sigma` that's higher relative to task variance, or add weight consolidation (e.g. only decay/update weights when reward is below some running baseline, an actor-critic-like baseline subtraction) so a working policy stops being overwritten once found.

All three result files are saved: `experiment_results/cluster_navigation.json` (pre-fix, dead motor), `experiment_results/cluster_navigation_with_exploration.json` (exploration-only), `experiment_results/cluster_navigation_batched_reward.json` (episode-batched reward, 1000 episodes — the result described above).
